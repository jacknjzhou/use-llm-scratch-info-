# 智能信息提取系统 - 技术方案

## 一、需求分析

### 核心需求
用户上传文件（如合同、报告、简历、发票等），自定义一组关键词/提取项，系统利用大模型从文件中提取对应信息，以结构化结果返回。

### 需求拆解
| 编号 | 需求点 | 说明 |
|---|---|---|
| R1 | 关键词自定义 | 用户可增删改提取项，每个提取项可带类型与描述 |
| R2 | 文件上传 | 支持 docx / pdf / txt / csv / xlsx / 图片等常见格式 |
| R3 | 智能提取 | 大模型理解文件内容，按关键词定位并提取信息 |
| R4 | 结构化输出 | 提取结果以 JSON 返回，前端可视化展示、可导出 Excel |
| R5 | 提取依据 | 每个提取值附带原文出处（页码/片段），便于人工核对 |

### 关键设计考量
1. **关键词 ≠ 简单字符串匹配**。用户定义的"关键词"实际是"提取意图"（如"甲方名称""付款金额"），必须由 LLM 做语义理解，而非正则/全文检索。
2. **上下文长度限制**。长文档（几百页 PDF）无法一次性塞给模型，需分块策略。
3. **提取准确性**。需要约束模型只输出 JSON，并对缺失字段做"未找到"标记而非编造（防幻觉）。
4. **批量场景**。多文件 × 多关键词的批量提取需要任务队列与进度反馈。

## 二、总体架构

```
┌──────────┐     ┌──────────────┐     ┌─────────────┐
│  前端     │────▶│  后端 API     │────▶│  LLM 服务    │
│ (上传/配置)│     │ (FastAPI)    │     │ (GLM/GPT等)  │
└──────────┘     └──────┬───────┘     └─────────────┘
                        │ 投递任务
                        ▼
                 ┌──────────────┐
                 │ Redis 消息队列 │
                 └──────┬───────┘
                        │ 消费
                        ▼
              ┌───────────────────┐
              │ Celery Worker 集群  │───▶ LLM API（异步并发调用）
              │ (提取/解析任务)      │
              └─────────┬─────────┘
                        │
          ┌─────────────┼─────────────┐
          ▼             ▼             ▼
    ┌──────────┐  ┌──────────┐  ┌──────────────┐
    │PostgreSQL │  │ 文件存储  │  │ Redis         │
    │(业务数据)  │  │(volume)  │  │(队列/结果缓存) │
    └──────────┘  └──────────┘  └──────────────┘
```

流程：上传文件 → API 存文件并落库 → 投递 Celery 异步任务 → Worker 解析分块 → 组装 Prompt（关键词+分块内容）→ 并发调用 LLM 提取 → 合并结果 → 写回 PostgreSQL → 前端轮询/WebSocket 获取进度与结果。

### 部署架构（Docker Compose）

```yaml
# docker-compose.yml 结构示意
services:
  api:        # FastAPI 服务，可 --scale api=2 横向扩展
  worker:     # Celery Worker，--scale worker=N 实现 N 路并发提取
  beat:       # 可选：定时清理过期任务/文件
  postgres:   # 业务数据库（持久卷）
  redis:      # Celery broker + result backend（持久卷）
  frontend:   # 静态资源，由 nginx 托管并反代 /api
```

- 所有状态（任务、结果、模板）入 PostgreSQL，容器无状态化，可任意扩缩容。
- 文件存储挂载 volume（一期），后续可平滑切换 OSS/S3。
- 环境变量统一由 `.env` 注入（数据库连接、LLM API Key、并发参数）。

## 三、技术选型

| 层次 | 选型 | 理由 |
|---|---|---|
| 后端 | Python + FastAPI | 生态成熟，原生 async，LLM SDK 丰富 |
| 文件解析 | python-docx / pypdf / openpyxl / pytesseract(图片OCR) | 按格式选择轻量库 |
| LLM | **可自定义配置**：统一走 OpenAI 兼容协议（GLM / DeepSeek / OpenAI / Ollama / vLLM 等均可接入） | 用户在界面配置 base_url + api_key + model，无需改代码 |
| 数据库 | **PostgreSQL 15+**（SQLAlchemy 2.0 + asyncpg） | 多用户生产级，JSONB 存提取结果，全文检索备用 |
| ORM/迁移 | SQLAlchemy + Alembic | 异步支持好，schema 版本化 |
| 任务队列 | **Celery + Redis**（broker & result backend） | 成熟稳定，Worker 可 `--scale` 横向扩展 |
| 并发模型 | API 层 asyncio；Worker 内 asyncio + 信号量并发调用 LLM；CPU 密集解析用 Celery prefork 多进程 | IO 与 CPU 分别处理，吞吐最优 |
| 前端 | Vue3 / React + Element UI | 快速搭建表单与结果表格 |
| 部署 | **Docker Compose**（api / worker / postgres / redis / frontend） | 一键部署，服务可独立扩缩 |

## 四、核心模块设计

### 4.1 关键词模板（提取项配置）

```json
{
  "template_name": "采购合同模板",
  "category": "合同类",                  // 模板分类，便于检索
  "description": "提取采购合同的关键商务信息",
  "fields": [
    {"key": "party_a", "label": "甲方名称", "type": "string", "desc": "合同中甲方全称"},
    {"key": "amount",  "label": "合同金额", "type": "number", "desc": "含税总金额"},
    {"key": "sign_date", "label": "签订日期", "type": "date", "desc": "YYYY-MM-DD 格式"}
  ]
}
```
- `key`：输出 JSON 的字段名；`label + desc`：给 LLM 的语义提示，是提取准确率的关键。
- 支持类型：string / number / date / boolean / enum(枚举选项)。

**模板管理机制（面向复用）：**
1. **按文件类型建模板**：一类文件（如"合同类""发票类""简历类"）对应一个模板，模板归属 `category` 分类，列表页可按分类筛选。
2. **勾选式复用**：发起提取任务时先选模板，模板内字段以**勾选列表**展示——用户可以只勾选本次需要的字段（如只提"金额"和"签订日期"），未勾选的字段不参与提取。
3. **模板生命周期**：保存（创建）→ 查看/预览 → 修改（增删改字段、改分类）→ 复制（基于已有模板派生新模板）→ 删除（有关联任务记录的模板软删除，保证历史结果可溯源）。
4. **版本留痕**：模板每次修改生成新 `version`，历史提取结果记录当时的 `schema_snapshot`（JSONB），避免模板改了导致旧结果对不上字段定义。
5. **导入导出**：模板支持 JSON 导入/导出，方便团队间共享与备份。

### 4.2 预置模板库（Seed 数据）

针对常见报销/商务文件类型，系统**出厂内置 8 套模板**（定义见 `docs/preset_templates.json`），首次启动随数据库迁移自动写入，用户可直接勾选复用，也可复制后修改：

| 模板名称 | 分类 | 核心提取字段 |
|---|---|---|
| 合同模板 | 合同类 | 甲方、乙方、合同金额、签订日期、合同期限、付款方式、合同编号 |
| 租赁合同模板 | 合同类 | 出租方、承租方、租赁物、租期起止、月租金、押金、付款周期 |
| 补充说明模板 | 合同类 | 关联主合同、签署方、补充内容摘要、变更条款、生效/签署日期 |
| 行程单模板 | 出行票据类 | 乘客姓名、证件号、出发/到达地、出发日期时间、到达时间、航班号/高铁车次、座位等级、车厢座位号、票价、税费、票据类型（航空/高铁/普速） |
| 住宿单模板 | 出行票据类 | 酒店名称、入住人、入住/离店日期、晚数、总金额、城市 |
| 餐饮流水单模板 | 出行票据类 | 商户名称、消费日期时间、菜品明细、消费总金额、支付方式 |
| 订购单模板 | 采购类 | 订单号、供应商、订购日期、商品明细、总金额、交货日期 |
| 付款截图模板 | 支付凭证类 | 付款人、收款人、金额、付款时间、交易单号、支付渠道、状态 |

预置模板设计原则：
1. **字段即答案清单**：每个字段都带 `label + desc`（给 LLM 的语义提示），desc 写明"在哪找、什么格式"，这是准确率的保证。
2. **新增 `array` 类型**：菜品明细、商品明细、变更条款等列表型信息，LLM 返回结构化数组。
3. **预置标记**：`is_preset=true` 的模板不可删除、只可"复制后修改"，保证出厂模板始终可用。
4. **付款截图属图片类**：走 OCR→文本→提取链路（该分类的文件解析自动启用 OCR 路径）。

### 4.3 文件解析模块
- 统一接口：`parse(file) -> List[Chunk]`，每个 Chunk 含文本、页码、位置索引。
- 分块策略：按 1500~2000 token 分块，保留少量重叠（overlap），避免信息被切断。
- 图片/扫描件走 OCR 后再分块。

### 4.4 LLM 提取模块（核心）

**Prompt 结构（单块）：**
```
你是信息提取助手。从下面给定的文本片段中，严格按照 fields 定义提取信息。

fields:
- party_a (string): 甲方名称
- amount (number): 合同金额
...

规则：
1. 只输出 JSON，不要输出任何其他内容。
2. 文本中找不到的信息，对应字段填 null，禁止编造。
3. 每个字段同时给出 evidence（原文片段，不超过50字）。

待提取文本：
<<<
{chunk_text}
>>>
```

**关键技术点：**
1. **JSON Mode / 结构化输出**：调用 LLM 时开启 JSON 约束，非法输出时自动重试（最多 2 次）。
2. **多块合并策略**：
   - 每块独立提取 → 合并时非空字段优先；
   - 同一字段多块都有值（如多期金额）→ 全部保留为列表，由用户确认。
3. **映射归一**：LLM 返回的 key 映射回用户定义的 key，类型校验（date 格式化、number 转数值）。
4. **并发控制**：Worker 收到任务后，内部用 asyncio + `asyncio.Semaphore` 对多个 chunk 并发调用 LLM（并发数可配，默认 5），失败块指数退避重试；多个 Worker 容器可水平扩展提升整体吞吐。

### 4.5 LLM 配置管理（可自定义）

**设计原则**：所有主流 LLM（GLM、DeepSeek、Kimi、OpenAI、Azure、本地 Ollama/vLLM 等）都兼容 OpenAI Chat Completions 协议，因此统一用一个 `openai` SDK 客户端，差异只在三个参数：`base_url / api_key / model`。这三个参数交给用户在界面配置，运行时从数据库读取，**切换供应商零代码改动**。

```sql
-- LLM 配置表
CREATE TABLE llm_config (
    id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name         VARCHAR(128) NOT NULL,          -- 配置名，如"GLM生产"、"本地Ollama"
    provider     VARCHAR(64)  NOT NULL,          -- openai-compatible（统一协议标识）
    base_url     VARCHAR(512) NOT NULL,          -- 如 https://open.bigmodel.cn/api/paas/v4
    api_key_enc  TEXT         NOT NULL,          -- AES 加密存储，密钥来自 .env 的 MASTER_KEY
    model        VARCHAR(128) NOT NULL,          -- 如 glm-4-flash / deepseek-chat
    params       JSONB DEFAULT '{}',             -- temperature / max_tokens / timeout 等
    is_default   BOOLEAN DEFAULT false,
    enabled      BOOLEAN DEFAULT true,
    created_at   TIMESTAMPTZ DEFAULT now()
);
```

**要点：**
1. **API Key 加密落库**：Fernet(AES) 对称加密，主密钥放 `.env`（`LLM_MASTER_KEY`），库泄露不泄露明文 key。
2. **多配置 + 默认配置**：支持保存多套 LLM 配置，发起提取任务时可指定用哪套，未指定用 `is_default`。
3. **连通性测试**：保存配置前调 `GET /models`（或发一条最小 chat 请求）做连通校验，前端即时反馈"连接成功/失败"。
4. **异步调用**：统一用 `AsyncOpenAI` 客户端，Worker 内多 chunk 并发天然兼容。
5. **JSON Mode 降级**：部分兼容端点不支持 `response_format=json_object`，做成可配项；不支持时走"prompt 强约束 + 解析失败重试"兜底。

**新增接口：**

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | /api/llm-configs | 新增 LLM 配置 |
| GET | /api/llm-configs | 配置列表（key 脱敏返回） |
| PUT | /api/llm-configs/{id} | 修改 / 设为默认 |
| POST | /api/llm-configs/{id}/test | 连通性测试 |
| DELETE | /api/llm-configs/{id} | 删除配置 |

### 4.6 数据库设计（PostgreSQL）

```sql
-- 提取模板（关键词配置，支持版本）
CREATE TABLE extract_schema (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name        VARCHAR(128) NOT NULL,      -- 模板名，如"采购合同模板"
    category    VARCHAR(64),                -- 文件类型分类，如"合同类"
    description TEXT,
    fields      JSONB NOT NULL,             -- [{key,label,type,desc}...]
    version     INT DEFAULT 1,              -- 每次修改 +1
    is_preset   BOOLEAN DEFAULT false,      -- 预置模板：不可删，可复制后修改
    is_deleted  BOOLEAN DEFAULT false,      -- 软删除，保证历史结果可溯源
    created_at  TIMESTAMPTZ DEFAULT now(),
    updated_at  TIMESTAMPTZ DEFAULT now()
);

-- 上传文件
CREATE TABLE upload_file (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    filename    VARCHAR(512) NOT NULL,
    storage_path VARCHAR(1024) NOT NULL,  -- volume 内相对路径
    mime_type   VARCHAR(128),
    size_bytes  BIGINT,
    status      VARCHAR(32) DEFAULT 'uploaded',  -- uploaded/parsed/failed
    created_at  TIMESTAMPTZ DEFAULT now()
);

-- 提取任务（异步任务主表）
CREATE TABLE extract_task (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    match_mode  VARCHAR(16) DEFAULT 'assigned',  -- assigned=指定模板 / auto=智能匹配
    schema_id   UUID REFERENCES extract_schema(id),  -- assigned 模式下的模板
    selected_fields JSONB,                    -- 本次勾选的字段 key 列表（模板复用）
    schema_snapshot JSONB,                    -- 发起任务时的模板快照，历史溯源
    status      VARCHAR(32) DEFAULT 'pending',   -- pending/running/succeeded/partially_succeeded/failed
    progress    SMALLINT DEFAULT 0,              -- 0~100
    total_chunks INT,
    done_chunks INT,
    error       TEXT,
    celery_task_id VARCHAR(64),                  -- 关联 Celery 任务，便于状态回查
    created_at  TIMESTAMPTZ DEFAULT now(),
    finished_at TIMESTAMPTZ
);

-- 任务-文件关联（一次任务可含多文件，逐文件记录模板匹配）
CREATE TABLE task_file (
    task_id  UUID REFERENCES extract_task(id),
    file_id  UUID REFERENCES upload_file(id),
    matched_schema_id UUID REFERENCES extract_schema(id), -- auto 模式下智能匹配结果
    match_confidence  NUMERIC(4,3),            -- 匹配置信度 0~1
    match_reason      TEXT,                    -- LLM 给出的匹配理由，结果页可溯源
    match_status      VARCHAR(16) DEFAULT 'bound', -- bound/need_confirm/unmatched
    status            VARCHAR(32) DEFAULT 'pending', -- 单文件处理状态
    PRIMARY KEY (task_id, file_id)
);

-- 提取结果（JSONB 存储，一个文件一个任务一条）
CREATE TABLE extract_result (
    id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    task_id    UUID REFERENCES extract_task(id),
    file_id    UUID REFERENCES upload_file(id),
    results    JSONB NOT NULL,           -- {field: {value, evidence, chunk}}
    coverage   NUMERIC(5,2),
    created_at TIMESTAMPTZ DEFAULT now()
);
CREATE INDEX idx_result_task ON extract_result(task_id);
```

要点：
- 提取结果用 **JSONB**：字段动态（用户自定义关键词），无需频繁改表；
- 任务进度（`progress / done_chunks`）由 Worker 直接更新 PG，前端轮询或 SSE 读取；
- Alembic 管理 schema 迁移，容器启动前自动 `upgrade head`。

### 4.7 多文件处理与智能模板匹配

**一次任务可上传多个文档**，任务分两种模式：

**模式 A：指定模板**（用户在发起页选了模板）
- 所选模板应用于本次全部文件（也支持对单个文件改派其他模板）；
- 每个文件独立解析 → 分块 → 提取 → 出结果，互不影响。

**模式 B：智能匹配**（未选模板，系统自动决策）
```
对每个文件：
1. 分类预判（轻量调用）
   - 取文件前 1~2 页文本（约 1500 token）+ 文件名
   - 调 LLM：「判断该文件属于哪个模板类别」
     候选项 = 当前启用模板列表（名称+分类+描述）
     输出：{matched_schema_id, confidence, reason}
2. 决策：
   - confidence ≥ 0.8  → 自动绑定模板，进入提取流程
   - 0.5 ≤ confidence < 0.8 → 绑定候选模板，但标记"待确认"，
     任务结果页高亮提示用户复核
   - confidence < 0.5 或无法判断 → 标记"未匹配"，
     用户在结果页手动指定模板后对该文件重跑
3. 匹配完成 → 按各自绑定的模板走正常提取流程
```

设计要点：
1. **分类调用很便宜**：只读前两页，一次短调用；N 个文件并发分类，通常几秒内完成。
2. **匹配结果留痕**：`task_file` 表记录 matched_schema_id / confidence / reason，结果页可见"为什么用了这个模板"。
3. **人工兜底**：低置信度和未匹配的文件永远有手动改派入口，不会静默出错。
4. **失败隔离**：多文件任务中某个文件解析/提取失败不影响其他文件，任务状态为"部分成功"。

### 4.8 结果结构
```json
{
  "task_id": "xxx",
  "file": "contract.pdf",
  "results": {
    "party_a": {"value": "XX科技有限公司", "evidence": "甲方：XX科技有限公司", "chunk": 3},
    "amount":  {"value": 1200000, "evidence": "合同总金额为人民币120万元", "chunk": 5},
    "sign_date": {"value": null, "evidence": null, "chunk": null}
  },
  "coverage": 0.87
}
```
`value=null` 明确表示"文中未找到"，配合 evidence 供人工快速核对。

## 五、任务流转与接口设计（初稿）

### 5.1 异步任务流转（多文件）
```
POST /api/extract（可含多个 file_ids，schema_id 可选）
  → API 校验、写 extract_task（match_mode=assigned/auto）+ task_file 逐条落库
  → celery.send_task("extract.run", task_id=...)
  → 立即返回 task_id（不阻塞）

Celery Worker（按文件粒度处理，文件间互不阻塞）:
  0. auto 模式：逐文件分类预判 → 绑定模板（低置信标记待确认）
  1. 状态 → running；解析文件 → 分块（CPU 多进程，prefork）
  2. asyncio.Semaphore 并发调 LLM 逐块提取（IO 并发）
  3. 每完成一块更新 done_chunks/progress
  4. 合并结果 → 写 extract_result → 单文件标记 succeeded/failed
  5. 全部文件处理完 → 任务状态（succeeded / partially_succeeded / failed）

前端:
  轮询 GET /api/tasks/{id}（或 SSE）展示进度；
  结果页按文件分组展示，"待确认/未匹配"文件提供模板改派入口
```

| PUT | /api/schemas/{id} | 修改模板（version 自动 +1） |

| DELETE | /api/schemas/{id} | 删除模板（软删除） |
| POST | /api/schemas/import · GET /api/schemas/{id}/export | 模板 JSON 导入/导出 |
| POST | /api/llm-configs | 新增 LLM 配置（base_url/key/model） |
| POST | /api/llm-configs/{id}/test | LLM 连通性测试 |
| POST | /api/extract | 发起提取任务（file_ids 多个；schema_id 可选，缺省走智能匹配；assigned 模式可带 selected_fields），立即返回 task_id |
| POST | /api/tasks/{id}/files/{file_id}/reassign | 对未匹配/待确认文件手动改派模板并重跑 |
| GET | /api/tasks/{id} | 查询任务进度与结果 |
| GET | /api/tasks/{id}/events | SSE 实时推送进度（可选） |
| GET | /api/tasks/{id}/export | 导出 Excel/JSON |

## 六、Docker Compose 部署

```yaml
# docker-compose.yml（示意）
services:
  api:
    build: ./backend
    command: uvicorn app.main:app --host 0.0.0.0 --port 8000
    environment: <<: *env          # DATABASE_URL, REDIS_URL, LLM_API_KEY...
    depends_on: [postgres, redis]
    volumes: [filedata:/app/storage]
  worker:
    build: ./backend
    command: celery -A app.worker worker -Q extract -c 4   # 单容器 4 并发进程
    depends_on: [postgres, redis]
    volumes: [filedata:/app/storage]
  postgres:
    image: postgres:16-alpine
    environment: [POSTGRES_DB, POSTGRES_USER, POSTGRES_PASSWORD]
    volumes: [pgdata:/var/lib/postgresql/data]
  redis:
    image: redis:7-alpine
    volumes: [redisdata:/data]
  frontend:
    build: ./frontend          # nginx 托管静态资源并反代 /api
    ports: ["80:80"]
volumes: [pgdata, redisdata, filedata]
```

- 首次启动：`docker compose up -d`，api 容器入口先执行 `alembic upgrade head`。
- 扩容：`docker compose up -d --scale worker=4`，多 Worker 共享同一 PG/Redis/文件卷。
- 配置全部走 `.env`，镜像内不含密钥。

## 七、实施计划（分期）

**一期（MVP，可运行）**
1. 后端骨架：FastAPI + PostgreSQL(SQLAlchemy/asyncpg) + Celery/Redis + Alembic
2. Docker Compose 全套部署（api / worker / postgres / redis / frontend）
3. LLM 配置管理：界面配置 base_url/api_key/model + 连通性测试 + key 加密存储
4. 关键词模板：创建/修改/复制/删除、分类管理、字段勾选复用、schema_snapshot 版本留痕
5. **预置模板初始化**：启动时自动写入 8 套出厂模板（合同/租赁合同/补充说明/行程单/住宿单/餐饮流水单/订购单/付款截图）
6. 多文件上传 + docx/pdf/txt 解析，解析任务走 Celery 异步
7. **模板决策**：指定模板 / 智能匹配双模式（分类预判 + 置信度决策 + 手动改派兜底）
8. LLM 提取：JSON 输出 + 未找到标记，chunk 级并发，文件级失败隔离
9. 前端：模板管理页（含预置模板）+ LLM 配置页 + 多文件上传/勾选字段发起任务 + 任务进度 + 按文件分组的结果核对页

**二期（增强）**
9. 长文档分块合并策略完善 + evidence 出处核对
10. 基础 OCR（容器内置 tesseract 中文包），打通付款截图等图片类文件提取
11. 模板 JSON 导入导出、团队共享
12. 结果导出 Excel；SSE 实时进度

**三期（规模化）**
13. 多文件批量提取、任务优先级与限流
14. 高精度 OCR（扫描版 PDF、拍照模糊件）
15. 提取结果人工确认与修正回流（few-shot 优化）
16. 对象存储（OSS/S3）替换本地卷

## 八、风险与对策

| 风险 | 对策 |
|---|---|
| 模型幻觉（编造不存在的信息） | prompt 强约束 + JSON 校验 + evidence 出处供核对 |
| 长文档超上下文 | 分块提取 + 合并策略 |
| 提取慢（大文件多关键词） | chunk 并发 + Celery 异步 + worker 横向扩容 + 进度反馈 |
| LLM API 限流/抖动 | 信号量限流 + 指数退避重试 + 失败块单独标记可重跑 |
| 自定义 LLM 端点行为不一致（无 JSON Mode、输出格式漂移） | response_format 做可配项，不支持时 prompt 强约束 + 失败重试兜底；保存配置时连通性测试 |
| 智能匹配误判（用错模板） | 置信度三级决策：≥0.8 自动绑定 / 0.5~0.8 待确认 / <0.5 未匹配；匹配理由留痕可溯源；手动改派兜底 |
| 多 Worker 共享文件卷的读写竞争 | 文件写入后只读；每文件归属单任务处理，结果落 PG |
| 容器重启丢任务 | Celery 任务状态落 PG（extract_task 表），启动时可扫描 pending/running 任务重新入队 |
| 扫描件/图片无文本（付款截图等） | 二期接入基础 OCR（tesseract 中文）；三期升级高精度 OCR |
| 关键词语义模糊导致提取偏差 | 引导用户填写 desc 描述；支持枚举限定 |
